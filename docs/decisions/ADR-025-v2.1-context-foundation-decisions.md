# ADR-025：V2.1 Project Context 基础决策 / V2.1 Project Context Foundation Decisions

- 状态：已接受；仅授权文档 / Status: Accepted; documentation only
- 日期：2026-10-07 / Date: 2026-10-07
- 决策范围：D113-A 至 D119-B / Decision scope: D113-A through D119-B
- 上位决策：`ADR-010`、`ADR-024` / Parent decisions: `ADR-010`, `ADR-024`

## 1. 背景 / Context

`ADR-024` 已确定 V2 先建设 Project Context，而不是直接建设知识库、RAG、Agent 或
平台集成。V2.1 需要进一步固定不可变 Context Revision 的物理存储、保留策略、V1
升级、Section 语义、最小 UI、捕获来源和并发控制，避免实现阶段把这些核心事实隐含
在文件路径或界面行为中。

`ADR-024` established that V2 begins with Project Context rather than a knowledge
base, RAG, Agents, or platform integration. V2.1 must now fix the physical
storage, retention, V1 upgrade, Section semantics, minimum UI, capture source,
and concurrency rules for immutable Context Revisions so that implementation
does not hide core facts in paths or UI behavior.

## 2. 决策 / Decisions

### D113-A：Project 内内容寻址对象存储 / Project-local content-addressed object storage

每个 Project 使用独立的 Context Object Store：

Each Project uses an isolated Context Object Store:

```text
<project-root>/context/objects/<sha256-prefix>/<sha256>
```

捕获使用 Operation Staging、流式 SHA-256、大小校验和原子发布。相同 Project 内相同
字节只保留一个物理对象；数据库中的引用和状态是所有权事实来源。磁盘文件存在本身
不代表有效 Revision，跨 Project 不去重。

Capture uses operation staging, streaming SHA-256, size verification, and atomic
publication. Identical bytes within one Project share one physical object. Database
references and states are the ownership source of truth. A file existing on disk
does not by itself create a valid Revision, and deduplication does not cross
Project boundaries.

### D114-B：有界保留、保护引用和磁盘门限 / Bounded retention, protected references, and disk gates

默认保留每个 Context Item 的当前 Revision 和上一个 Revision。被保留的 Analysis、
Citation、Context Pack 引用，或被用户手动保护的 Revision，不受该数量上限影响。更早
且无引用、未保护的 Revision 只成为清理候选，不自动删除；清理必须先显示影响并由
用户确认。

By default, each Context Item retains its current and previous Revisions. A
Revision referenced by retained Analysis, Citation, or Context Pack data, or
manually protected by the user, is exempt from that count. Older unreferenced
and unprotected Revisions become cleanup candidates only; they are never deleted
automatically, and cleanup requires impact preview plus user confirmation.

每个 Project 的 Context Store 默认软提醒阈值为 10 GiB；阈值可配置。捕获前若预计发布
后可用磁盘空间低于 2 GiB，则阻止新的捕获。软阈值只提醒和展示影响，不自动清理，
2 GiB 最低剩余空间是安全阻断门。

The default Context Store soft-warning threshold is 10 GiB per Project and is
configurable. New capture is blocked when projected free disk space after
publication would fall below 2 GiB. The soft threshold warns and previews impact
without automatic cleanup; the 2 GiB minimum free-space reserve is a safety gate.

### D115-A：V1 Project 原地前向升级 / In-place forward upgrade for V1 Projects

打开当前 V1 Workbench Project 时，系统识别模型版本、展示升级内容并要求用户确认。
确认后先备份 `project.sqlite`，验证备份，再运行基于当前 Alembic Head 的前向 Migration，
校验 V1 Original、Source、Workspace、Working 和 Event 事实，最后才更新模型版本。

When opening a current V1 Workbench Project, PIG detects its model version,
explains the upgrade, and requires user confirmation. It then backs up and
verifies `project.sqlite`, runs a forward migration from the current Alembic
head, validates V1 Original, Source, Workspace, Working, and Event facts, and
only then advances the model version.

不做双写或长期双模型读取。失败时保留备份、停止 Project 写入并给出可重试诊断；不得
在不完整 Schema 上继续运行。升级不得重写 Original 或 Working 字节。

There is no dual-write or long-lived dual-model reader. On failure, PIG retains
the backup, stops Project writes, and presents retryable diagnostics; it cannot
continue on a partial schema. Upgrade never rewrites Original or Working bytes.

### D116-A：扁平有序 Section 与软删除 / Flat ordered Sections with soft deletion

V2.1 只支持 Project 内扁平、可排序的 Section，不支持嵌套 Section。Context Item 与
Section 通过显式 `ContextPlacement` 建立多对多关系，一个 Item 可以位于多个 Section。

V2.1 supports only flat, ordered Sections within a Project and does not support
nested Sections. Context Items and Sections use explicit many-to-many
`ContextPlacement` records, allowing one Item to appear in multiple Sections.

删除 Section 是软删除：保留 Section 和 Placement 事实，不删除 Context Item、Revision、
Annotation、Workspace 或 Original。没有任何有效可见 Placement 的 Active Item 显示在
虚拟系统分组 `Unsectioned`；它不是持久化 Section。恢复 Section 后原 Placement 重新
生效。

Section deletion is soft: Section and Placement facts remain, while Context
Items, Revisions, Annotations, Workspace, and Originals remain untouched. An
active Item with no effective visible Placement appears in the virtual system
group `Unsectioned`, which is not a persisted Section. Restoring the Section
reactivates its existing Placements.

### D117-A：同窗口双视图最小 UI / Minimum same-window dual-view UI

同一 Project 窗口提供 `[Workspace] [Project Context]` 切换。Project Context 首期只由
Section 列表、Item 列表和 Item Details 构成。Workspace 右键菜单提供
`Add to Project Context`。UI 只发起 Application Action 和展示 Query Result，不直接
写数据库或复制文件。

The same Project window provides `[Workspace] [Project Context]` switching. The
initial Project Context view contains only a Section list, Item list, and Item
Details. The Workspace context menu provides `Add to Project Context`. The UI
only invokes Application Actions and renders Query Results; it neither writes
the database nor copies files directly.

V2.1 不实现 AI、时间线、思维导图、正文预览、RAG 或模型设置页面。

V2.1 does not implement AI, timelines, mind maps, document-content preview,
RAG, or model-settings pages.

### D118-B：确定性选择捕获来源 / Deterministic capture-source selection

对已 Materialize 的 Workspace Item，捕获前先刷新 Working 状态，再捕获当前 Working
字节。若当前 Working 缺失或不可读，阻止捕获并记录明确失败，不回退到旧 Working 或
Original。

For a materialized Workspace Item, PIG first refreshes Working state and then
captures the current Working bytes. If the current Working file is missing or
unreadable, capture is blocked with an explicit failure; PIG does not fall back
to stale Working bytes or Original data.

对 Virtual Workspace Item，系统直接从 Source 通过现有受控 Materialization 能力将
字节写入 Context Staging；不得启动 Host Application，也不得为了建立 Context 强制创建
Working Artifact。两条路径最终执行相同的 Hash、容量、原子发布和数据库提交规则。

For a virtual Workspace Item, PIG streams bytes from Source through the existing
controlled materialization capability into Context staging. It neither launches
a Host Application nor forces creation of a Working Artifact merely to build
Context. Both paths then use the same hash, capacity, atomic publication, and
database-commit rules.

### D119-B：独立 Context 乐观并发版本 / Independent Context optimistic-concurrency revision

Project 新增独立的单调递增 `context_revision`，与现有 `workspace_revision` 分离。
Workspace 捕获读取并校验预期 Workspace 状态；Context 写 Action 必须携带并校验预期
`context_revision`。成功的 Context 事务只递增 `context_revision`，不得借用或重置
`workspace_revision`。

Project gains an independent monotonic `context_revision`, separate from the
existing `workspace_revision`. Workspace capture reads and validates expected
Workspace state, while Context write Actions carry and validate an expected
`context_revision`. A successful Context transaction increments only
`context_revision` and cannot reuse or reset `workspace_revision`.

冲突返回结构化 `CONTEXT_CONFLICT` 或 `WORKSPACE_CHANGED_DURING_CAPTURE`，由用户刷新
后重试；系统不得静默覆盖另一操作的结果。

Conflicts return structured `CONTEXT_CONFLICT` or
`WORKSPACE_CHANGED_DURING_CAPTURE` outcomes for refresh and retry. PIG never
silently overwrites another operation's result.

## 3. 结果 / Consequences

正面结果：Context 字节具备稳定身份；V1 事实不被重写；文件夹工作流与项目上下文彼此
独立；版本、容量、清理和并发行为可测试且可解释。

Positive outcomes: Context bytes gain stable identity, V1 facts remain intact,
folder work and Project Context remain separate, and version, capacity, cleanup,
and concurrency behavior becomes testable and explainable.

代价：每个 Project 增加独立对象存储和数据库表；捕获会产生额外磁盘占用；升级和清理
需要显式预检；同一文件的 Workspace 更新不会自动成为新的 Context Revision。

Costs: each Project gains an object store and new database tables, capture uses
additional disk space, upgrades and cleanup require explicit preflight, and a
Workspace update does not automatically become a new Context Revision.

## 4. 明确不做 / Explicit non-goals

- 不实现内容提取、FTS5、Embedding、Vector Store 或 RAG；
- 不实现模型调用、AI Chat、Agent、Workflow、Automation 或 MCP；
- 不实现真实平台 Adapter、云同步或多用户协作；
- 不实现嵌套 Section、时间线、思维导图或正文预览；
- 不自动清理 Revision，也不改变 Original Data Policy。

- No content extraction, FTS5, embeddings, vector store, or RAG.
- No model calls, AI chat, Agents, Workflows, Automation, or MCP.
- No real platform adapters, cloud sync, or multi-user collaboration.
- No nested Sections, timelines, mind maps, or content preview.
- No automatic Revision cleanup and no change to the Original Data Policy.

## 5. 授权边界 / Authorization boundary

本 ADR 只固定 V2.1 决策并授权同步双语规划与实施文档。它不授权创建 Migration、修改
Schema、Python、UI、测试代码或依赖。开始 V2.1 实现仍需产品负责人明确批准。

This ADR only fixes V2.1 decisions and authorizes synchronized bilingual planning
and implementation documents. It does not authorize migrations, schema changes,
Python, UI, test code, or dependencies. V2.1 implementation still requires
explicit product-owner approval.
